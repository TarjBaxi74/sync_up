01
Fact tables
The ledger of your warehouse
A fact table records every measurable business event. One row per transaction, click, sale, or return. It is the centrepiece of any dimensional model.
Analogy — ShopFlow

Think of the cashier's receipt printer at a supermarket. Every time a customer checks out, a new receipt is printed — item, quantity, price, date, store. That growing stack of receipts is your fact table. It records what happened, not who or where.

A fact table has two kinds of columns. Foreign keys are pointers — they link each row to a dimension table that explains the context. Measures are the actual business numbers you want to analyse — revenue, quantity, delivery time, discount applied.

Foreign keys
Pointers to dimension tables. They do not store names or labels — just IDs. The customer_key tells you which customer, but the name lives in dim_customer.
Measures
The actual business numbers. These are what gets summed, averaged, counted. total_amount, quantity, discount_amount are all measures.
Characteristics
Billions of rows — grows every minute
Append-only — rows are added, rarely updated
Mostly numbers + IDs, minimal free text
Partitioned by date for query performance
Three types of fact tables
Transaction fact
One row per event. The most common type. Grows constantly as events happen.
fact_orders: every order placed on ShopFlow
Snapshot fact
One row per time period. Captures a state at a point in time — balances, inventory counts.
fact_inventory_daily: stock level per product per day
Accumulating fact
Tracks a process through multiple stages. The same row is updated as it progresses.
fact_order_lifecycle: placed → packed → shipped → delivered
fact_orders — every row is one ShopFlow order. Numbers live here; names and labels live in dimension tables.
02
Dimension tables
The context around every event
If fact tables answer "what happened", dimension tables answer who, what, where, when, and how. They are the reference books of the warehouse.
Analogy — ShopFlow

The fact table says: customer_key=88, product_key=334, amount=₹1299. The dimension tables decode this: customer 88 is Priya Sharma from Bengaluru, Gold tier. Product 334 is Noise Buds Z1, Electronics, Sony. That is dimension data.

ShopFlow has five dimension tables. Together they wrap around fact_orders and answer every analytical question an analyst might ask.

03
Star schema
The default choice for analytics
One fact table at the centre. Dimension tables connect directly to it — flat, denormalised, no sub-tables. The shape looks like a star.
How it works

Imagine a wheel. The hub is fact_orders. Each spoke leads to a dimension table — customer, product, date, payment, location. Every dimension is one join away from the fact table. That is what makes star schemas fast.

ShopFlow star schema — fact_orders at the centre, five dimension tables as direct spokes
StructureFact table + flat (denormalised) dimension tables
Joins per queryFew — 1 per dimension
Query speedFast
StorageHigher — some attribute data repeats across rows
ComplexityLow — easy to understand
BI tool supportExcellent — Power BI, Tableau, Looker are optimised for star
ShopFlow examplefact_orders JOIN dim_customer — one hop, done
04
Snowflake schema
Normalised for scale and consistency
Same core idea as star, but dimension tables are broken down into sub-tables. A product links to a category, which links to a department. The branching shape looks like a snowflake.
How it differs

In the star schema, dim_product contains category = "Electronics" repeated across thousands of rows. In snowflake, "Electronics" lives once in dim_category, and dim_product just holds a foreign key pointing to it.

ShopFlow snowflake — product normalises into category → department; customer normalises into city → state
StructureFact + normalised dimension sub-tables (2–3 levels deep)
Joins per queryMany — traverses sub-tables
Query speedSlower
StorageLower — no duplicated attribute data
ComplexityHigher — more tables to navigate
Data integrityStronger — one source of truth per attribute
ShopFlow examplefact → dim_product → dim_category → dim_dept (3 hops)

Sample queries
The schema in action
Real SQL on the ShopFlow star schema. Each query answers a business question an analyst or ML engineer would actually ask.
Revenue by city — Q1 2024
SELECT dc.city, SUM(fo.total_amount) AS revenue, COUNT(*) AS orders
FROM fact_orders fo
JOIN dim_customer dc USING (customer_key)
JOIN dim_date dd USING (date_key)
WHERE dd.year = 2024 AND dd.quarter = 1
GROUP BY dc.city ORDER BY revenue DESC LIMIT 10 -- top 10 cities by revenue
Top product categories by order volume — last 30 days
SELECT dp.category, dp.brand, COUNT(*) AS orders, AVG(fo.total_amount) AS avg_order_value
FROM fact_orders fo
JOIN dim_product dp USING (product_key)
JOIN dim_date dd USING (date_key)
WHERE dd.full_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)
GROUP BY dp.category, dp.brand ORDER BY orders DESC
Payment method split — by customer tier
SELECT dc.tier, dpay.method, COUNT(*) AS txns, SUM(fo.total_amount) AS gmv
FROM fact_orders fo
JOIN dim_customer dc USING (customer_key)
JOIN dim_payment dpay USING (payment_key)
GROUP BY dc.tier, dpay.method
ORDER BY dc.tier, gmv DESC -- which payment methods do Gold/Platinum customers prefer?
Weekend vs weekday orders — by region
SELECT dl.region, dd.is_weekend, COUNT(*) AS orders, SUM(fo.total_amount) AS revenue
FROM fact_orders fo
JOIN dim_location dl USING (location_key)
JOIN dim_date dd USING (date_key)
GROUP BY dl.region, dd.is_weekend -- do southern regions shop more on weekends?
Key takeaways
01

Fact tables record what happened

Numbers and foreign keys only. Large, append-heavy, grows constantly. Three types: transaction, snapshot, and accumulating.

02

Dimension tables explain the context

Who, what, where, when. Text-rich, smaller, changes slowly. They make the numbers in fact tables meaningful.

03

Star schema is the default

Flat dimensions, one join per dimension, fast queries. Ideal for most analytics, BI tools, and teams starting out.

04

Snowflake when scale and consistency matter

Normalised sub-tables, lower storage, stricter integrity. More complex to build and query — use when the trade-off is worth it.

05

Design is about making data easy to trust and query

A well-designed schema means analysts spend less time wrangling data and more time finding insights.
